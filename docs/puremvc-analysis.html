所有核心角色接口（ICommand、IMediator、IProxy）以及门面接口 IFacade 都继承自 INotifier，这意味着 MVC 三层的任何角色都具备发送通知的能力，实现了松耦合的跨层通信。

接口职责
INotifier公共基接口，提供 SendNotification 便捷方法
INotification通知消息体，携带 Name（路由键）、Body（数据）、Type（可选分类）
IObserver观察者，封装回调方法 + 上下文对象，是发布/订阅机制的底层载体
IFacade门面接口，统一暴露 Model/View/Controller 的全部操作
IModel数据层接口，管理 IProxy 的注册/检索/移除
IView视图层接口，管理 IMediator 和 IObserver 的注册/广播
IController控制层接口，管理 ICommand 的注册/执行
ICommand命令接口，定义 Execute(INotification)
IMediator中介者接口，声明感兴趣的通知列表和处理方法
IProxy数据代理接口，持有数据对象并提供生命周期钩子

AppFacade 扩展点

  • InitializeController()：注册了项目中约 80+ 条 Command 映射，包括启动流程（StartUpCommand、LoginCommand）、网络协议响应（以 Sproto TagName 为通知名）、业务命令等。
  • RegisterMediator 增强：额外维护 m_viewMap（ViewBinder → Mediator）和 m_MediatorMap（名称 → Mediator），支持通过 Unity 组件快速查找。
  • GlobalMediator：RegisterGlobalMediator / RemoveGlobalMediator 管理不随 UI 生命周期销毁的全局 Mediator。
  • SendNotification 增强：除标准 PureMVC 通知链路外，额外通知 SubViewManager，支持子视图系统。
  • SendSproto：封装网络协议发送，通过 NetProxy 代理。

五、核心三元组详解

5.1 Model — 数据仓库

ConcurrentDictionary<string, IProxy> proxyMap
  • 单例模式，通过 GetInstance() 获取
  • 内部用 ConcurrentDictionary 存储所有 IProxy，以 ProxyName 为键
  • RegisterProxy 时自动调用 proxy.OnRegister()
  • RemoveProxy 时自动调用 proxy.OnRemove()
  • 职责纯粹：只做 Proxy 的 CRUD，不参与通知分发

5.2 View — 观察者中心 + Mediator 仓库

ConcurrentDictionary<string, IMediator> mediatorMap
ConcurrentDictionary<string, IList<IObserver>> observerMap

View 是整个通知系统的核心枢纽，承担两个职责：

  1. Observer 管理：维护 notificationName → List<IObserver> 的映射表。NotifyObservers 时先复制列表再遍历，避免迭代中修改集合。
  2. Mediator 管理：注册 Mediator 时，自动调用 ListNotificationInterests() 获取其感兴趣的通知名，为每个通知名创建一个 Observer（封装 HandleNotification 方法），注册到 observerMap。移除时反向清理。

这是 PureMVC 最精妙的设计之一：Mediator 不需要手动订阅/退订通知，框架通过 ListNotificationInterests + 自动 Observer 注册实现了声明式的事件绑定。

5.3 Controller — 命令调度器

ConcurrentDictionary<string, Func<ICommand>> commandMap
IView view  // 持有 View 引用
  • 维护 notificationName → Func<ICommand> 的映射（工厂函数，每次执行创建新实例）
  • RegisterCommand 时，同时向 View 注册一个 Observer，回调指向 ExecuteCommand
  • 当 View 广播通知时，Observer 触发 ExecuteCommand，从 commandMap 取出工厂函数，创建 Command 实例并执行

5.4 SimpleCommand vs MacroCommand

SimpleCommandMacroCommand
用途单一业务逻辑组合多个子命令
重写方法Execute()InitializeMacroCommand()
执行方式直接执行FIFO 顺序执行所有子命令
子命令无通过 AddSubCommand() 添加

5.5 Notifier — 通知发送基类

所有 MVC 角色的公共基类。通过持有 Facade 单例引用，让子类可以直接调用 SendNotification 而无需关心底层的 Observer 机制。

protected IFacade Facade => Facade.GetInstance(() => new Facade());

public virtual void SendNotification(string name, object body = null, string type = null)
{
    Facade.SendNotification(name, body, type);
}

九、设计模式总结

门面模式 (Facade)
Facade 类统一封装 Model/View/Controller，对外提供单一入口
单例模式 (Singleton)
Model、View、Controller、Facade 均为单例，通过 GetInstance 工厂方法获取
观察者模式 (Observer)
Observer + View.observerMap 实现发布/订阅通知机制
命令模式 (Command)
SimpleCommand / MacroCommand 封装业务逻辑为可执行对象
中介者模式 (Mediator)
Mediator 解耦 View 组件与业务逻辑层
代理模式 (Proxy)
Proxy 封装数据访问，隔离数据层与其他层
工厂方法 (Factory)
Func<ICommand> 工厂函数延迟创建 Command 实例，每次执行都是新对象
组合模式 (Composite)
MacroCommand 组合多个子命令，按 FIFO 顺序执行
